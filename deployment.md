# Checkpoint product deployment

This upgrade replaces the fixture comparison with a durable private delivery workspace. The Vercel frontend/native JSON relay and Railway backend must be released together after source/CI/browser review. A prior laboratory deployment at the same host is not evidence that this product revision is deployed.

## Runtime and durable storage

Use Node.js 24+ for `node:sqlite`. There are no npm runtime packages. Python 3.11+ remains only for historical research tests. Production starts with `node scripts/launch.mjs` (`npm start`). Local Work Mode preview uses the separate `npm run dev` entrypoint; it permits the managed local root account but refuses `NODE_ENV=production` or a Railway environment. It does not relax the production launcher or its privilege drop. `PORT` defaults to 3000; preview `--host 0.0.0.0 --port 4173 --strictPort` flags are supported.

Set `DATA_DIR=/data/checkpoint` and mount a persistent Railway volume at `/data`. Never put the production database under `/tmp`, the image filesystem, a static frontend or an ephemeral function. Unwritable/invalid storage fails startup; there is no temporary fallback. The SQLite ledger uses WAL, FULL synchronous commits, foreign keys, bounded WAL checkpoints and a 64 MiB main-file ceiling. The volume should reserve at least 128 MiB, with monitoring and tested backups. Workspace data is private application data, not encrypted against an operator who can read the volume.

The normal image uses `USER node` (UID/GID 1000). For Railway's root-owned new volume, configure `RAILWAY_RUN_UID=0` and `DROP_PRIVILEGES=1`. The launcher accepts only trusted `/data/checkpoint` in production, rejects symlink ancestry, opens `/data` with directory/no-follow flags and sets that parent to traversable 0711, then opens only the child directory and changes its ownership to 1000:1000 and mode 0700. It never recursively changes existing files. It clears supplementary groups, sets GID then UID to 1000 and verifies the result **before importing the server**. Any initialization/drop failure exits before HTTP starts. Preexisting root-owned SQLite files require deliberate operator repair; no recursive chown is attempted.

The managed authoring filesystem rejects descriptor `fchown` with EINVAL, so that exact privileged local branch is capability-skipped here, not claimed verified. Normal nonroot operation, fail-closed root refusal and durable storage are tested; CI also checks the container's UID is 1000. The actual Railway root-volume/drop branch must be checked after deployment using readiness `runtimeUid: 1000` and restart persistence.

One service process owns a database. Ownership is serialized in SQLite and checked against the operating-system PID/start identity; a live competing owner is refused. Restart converts interrupted delivering attempts to unknown before admitting work. It does not resend queued or uncertain requests. `railway.json` requests one replica, zero overlap and a ten-second shutdown drain. Do not enable multi-region/extra replicas or mount the database concurrently across hosts.

## API

- `POST /api/workspaces {}` returns one random 32-byte bearer token and workspace expiry. Only its SHA-256 hash is stored. Workspace creation is globally limited to five per minute and 500 retained workspaces.
- All delivery/export routes require `Authorization: Bearer <workspace token>`. Never place that token in a URL. Every query/action also binds the delivery to that workspace; another workspace sees 404.
- `POST /api/deliveries` accepts `destination`, `reference`, `payload`, optional `idempotency`, optional `lookup`, and an ignored/never-persisted `credential` field. It durably creates queued state without sending. Reference is unique within the workspace. JSON payload is capped at 16 KiB and sent unchanged.
- `POST /api/deliveries/:id/send {credential?}` explicitly dispatches the queued intent. Journal and attempt are committed before the actual POST. The receiver gets `X-Checkpoint-Reference` plus any declared idempotency header.
- `POST /api/deliveries/:id/reconcile {credential?}` performs only a real GET. Lookup specifies `url`, `recordsPointer` and `referencePointer`; the response must contain at most 100 structurally valid records and exactly one exact reference match. No match, duplicates, malformed data, network failure or non-2xx lookup requests review and never permits retry merely from absence.
- `POST /api/deliveries/:id/retry {credential?,riskConfirmed?}` is explicit. It is safe only after a proven pre-transmission failure or a user-declared receiver idempotency contract. Otherwise `riskConfirmed: true` is required and journaled as acknowledged duplicate risk. A delivered job cannot be resent. Declaring idempotency does not make an endpoint implement it.
- `GET /api/deliveries`, `GET /api/deliveries/:id`, `DELETE /api/deliveries/:id` and `GET /api/export` provide private history, details, inactive-history deletion and bounded export. Exports omit access keys and credential headers.

Credential input is `{name,value}` for the current action only. Hop-by-hop, Host, forwarded, framing and reserved reference headers are prohibited. A credential cannot overwrite the idempotency header. There is no saved credential store. Incoming workspace Authorization is never copied to an outbound destination. Saved response bodies from credentialed operations are wholly omitted; other previews redact common secret fields and are truncated to 1024 characters. No response headers or raw bodies are retained. Payloads/URLs remain private persisted user inputs and may themselves contain secrets if the user puts them there.

States are queued, delivering, delivered (HTTP acknowledged or configured reference proof), unknown, failed (pre-transmission), and needs_review. A 500 or redirect after POST dispatch may follow a committed effect and is ambiguous. Timeouts and crashes remain unknown. No background/autonomous retry exists. Lookup reference proof does not claim payload-hash matching or independent business settlement.

## Egress and resource bounds

Every outbound destination and lookup must be HTTPS on port 443 without embedded credentials or fragments. DNS lookup checks **all** answers; private, loopback, link-local, multicast, documentation, translated/mapped/tunneled and known metadata/control-plane addresses including Azure 168.63.129.16 are rejected. A validated IP is pinned through a custom lookup while normal TLS certificate/SNI verification stays on. There is no redirect following or ambient HTTP proxy. A second DNS resolution cannot silently substitute a private address.

There are at most two active outbound operations, 20 accepted mutations per minute globally, 50 deliveries per workspace, 500 retained deliveries overall and 20 attempts per delivery. Tokens/history expire after seven days; pruning cascades private records. A JSON request is at most 32 KiB, outbound JSON payload 16 KiB, response 32 KiB, saved preview 1024 characters and workspace export one MiB. DNS has a 1.5-second budget and HTTPS a five-second absolute budget. A slow/disconnected client cannot trigger an automatic retry. Shutdown stops admissions, lets work finish and aborts after seven seconds; ambiguous active outcomes are recorded when possible, or recovered unknown after restart.

CORS accepts only exact `PUBLIC_ORIGIN=https://steel-checkpoint.vercel.app` or a direct actual-socket same-origin request. Forwarding headers never establish trust. No-Origin clients still need a workspace token for private operations. This boundary is not authentication against direct API callers; the workspace key is the authorization secret.

## Vercel native JSON relay

`api/[...path].js` is a native Vercel Node function. It accepts only explicit product API paths, serializes the parsed JSON body once, and forwards only workspace Authorization, JSON Content-Type and the fixed public Origin to `https://checkpoint-production-81f4.up.railway.app`. It does not forward browser Host, cookies, Content-Length or arbitrary headers. Redirects, oversized responses and non-JSON backend results fail closed. On relay timeout the UI must refresh private history before another action because the backend may have acted.

`vercel.json` retains only public health rewrites; product `/api/*` is handled by the native function. Static frontend assets are built by `scripts/build-frontend.mjs` into `dist`. No fixture/worker computation runs in the Vercel function, and the SQLite volume remains exclusively on Railway. A changed backend hostname requires deliberate relay/health destination updates and a coordinated release.

## Verification and release

`npm test` runs preserved Python research regressions, the segregated legacy laboratory HTTP tests, product real-HTTP controlled-transport tests and frontend presentation/theme tests. Product tests cover actual receiver commit then disconnect, no automatic retry, receiver 500/redirect ambiguity, reference lookup, workspace isolation, restart durability/process death, credential omission, private export, metadata/mapped-IP rejection, DNS pinning/TLS options and native relay serialization. The local controlled adapter uses a real ephemeral HTTP receiver; it is not a live public TLS-provider test or vendor integration.

`npm run smoke` verifies a private workspace, durable queued intent and export without making any external POST. CI builds/runs the nonroot Docker image with writable bounded `/data` and read-only code, checks readiness and creates a queued intent. A hosted product revision must also be tested against a consenting real public HTTPS receiver, restarted on the persistent volume, then checked from the actual Vercel browser including unknown/reconciliation and private-history paths. The old fixture site's successful deployment does not satisfy those product checks.
